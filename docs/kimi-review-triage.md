# Kimi 前端视觉评审分级与验收标准

> 来源：Kimi《女神之殇：无旗者》前端视觉评审报告。本文只做任务分级与验收口径整理，不代表已经实施。

## 总体结论

- 当前暗底、圣金、衬线大字与低模战场的视觉方向成立。
- 首要风险是运行时规则、渲染层和内容层未接通，导致 HUD 信息与真实战斗状态不一致。
- 继续坚持轻量方案：不引入重型依赖，不改成全 3D 开放世界，完整资源继续以小于 100MB 为硬约束。

## P0：阻塞体验，必须先修

### P0-1 接通规则层、渲染层与内容层

问题：运行时仍使用 `render/battlefield.ts` 内的简化规则；`game/battle.ts` 的信念伤害、敌方意图、阶段制和 `content/*` 数据没有进入实际游戏。

验收标准：

- `render/` 只负责显示和输入转发，战斗判定来自 `game/`，剧情与阵营数据来自 `content/`。
- HUD 中生命、信念、移动力与当前规则状态实时一致，不显示不会变化的“死数据”。
- 敌方下一步意图在行动前可见，且与实际执行结果一致。
- 移动力统一为最终规则值，不再出现规则层与画面层 2 格/3 格漂移。
- 现有战斗规则测试通过，并补充至少一条 UI 状态映射测试或人工验收记录。

### P0-2 统一阵亡单位表现

问题：敌方生命归零后仍留在棋盘上，敌我阵亡处理不对称。

验收标准：

- 任意单位生命归零后不再可选、不可阻挡格子、不可被再次攻击。
- 敌我双方调用同一套状态同步逻辑。
- 阵亡先播放约 0.5–1 秒倒地或淡出反馈，再隐藏模型；减少动画时可直接切换到静态结果。
- 胜负判定以规则状态为准，画面中不存在“幽灵单位”。

### P0-3 明确阶段制与回合节奏

问题：当前每个我方单位行动后敌人立即反击，与规则层的阶段制冲突，且 HUD 没有回合信息。

验收标准：

- 采用阶段制：我方可行动单位处理完成后统一进入敌方阶段。
- HUD 始终显示“第 N 回合 · 我方/敌方阶段”。
- 已行动单位有稳定、非纯文字的视觉区分，例如底座变灰。
- 玩家能看到剩余可行动单位数量。
- 阶段切换有明确但短促的视觉反馈，不能阻塞连续操作。

### P0-4 补齐战棋基础操作引导

问题：缺少移动范围、攻击目标、悬停和取消选择反馈。

验收标准：

- 选中单位后立即高亮所有合法可达格；非法格不高亮且不能移动。
- 当前可攻击敌人具有明显红色标记，且不只依赖模型颜色。
- 鼠标悬停可交互目标时光标或棋子状态发生变化。
- 再次点击已选单位可取消选择，并清除范围与目标标记。
- 上述效果使用现有 Three.js 能力或轻量材质/实例化实现，不新增重型依赖。

## P1：明显提升品质，应在 P0 后完成

### P1-1 补齐叙事界面基本件

验收标准：

- 对话具有明确说话人名条，不再出现无署名引用。
- 文本采用逐段淡入等轻量进入动效，不使用拖慢阅读的打字机效果。
- 选项有悬停、键盘焦点与结果倾向提示。
- 界面显示章节序号或章节进度锚点。
- 阵营名称、人物名条或关键词使用 `content/world.ts` 定义的阵营色，并保证正文可读性。

### P1-2 固化中文字体方案

验收标准：

- Windows 与 macOS 上分别截图对比，标题气质和正文宽度不出现明显漂移。
- 优先为标题/章节内嵌子集化 WOFF2，目标约 200KB；正文使用明确的系统中文衬线字体栈。
- 字体加载失败时仍有可接受的回退方案，不阻塞首屏。
- 新增字体后完整资源仍远低于 100MB。

### P1-3 重做单位卡和战报层级

验收标准：

- 生命与信念采用条形加数值展示；生命低于或等于 30% 时出现濒危反馈。
- 我方、敌方单位卡均可查看，并有不只依赖颜色的阵营区分。
- 战况区显示最近三条有效事件，包括行动者、目标、伤害或状态变化。
- 单位卡信息变化与棋盘表现同步，不出现上一单位的残留状态。

### P1-4 增加响应式中间档

验收标准：

- 除 720px 外增加约 1100px 的平板断点。
- 721–1100px 宽度下棋盘仍是主视觉，侧栏不显著挤压棋盘。
- 手机端关键行动按钮固定在可视区域底部，不要求滚动后才能结束行动。
- 320px 宽度下选项按钮文字可换行但等高，页面无横向溢出。
- 桌面、平板竖屏、手机各完成一轮剧情和一场战斗的人工冒烟测试。

## P2：打磨项

### P2-1 轻量动作插值

- 移动使用 8–12 帧插值，攻击有约 200ms 前扑。
- 动画期间重复输入不会造成状态错乱。

### P2-2 完整支持减少动画偏好

- `prefers-reduced-motion: reduce` 同时停用 CSS 与 Three.js 的火焰摇曳、尘埃、脉动和非必要插值。
- 关键状态变化仍有静态反馈。

### P2-3 增加色弱可读性

- 敌我除颜色外还使用底座形状区分，例如我方圆座、敌方方座。
- 灰阶截图下仍能识别阵营、可行动状态与攻击目标。

### P2-4 防止误退出

- 有战斗进度时首次点击退出显示确认或进入二次确认状态。
- 取消退出后保留当前战斗状态。

### P2-5 清理仓库残留

- 删除确认无用的 `src/render/*.bak`、测试 GLB 与运行日志。
- 构建产物和日志遵循 `.gitignore`，清理前确认没有被运行时代码引用。

### P2-6 强化结算反馈

- 正负变化有颜色、方向符号和文字三重反馈。
- 结算区域预留累计真相、阵营信誉等后续数值位置。

### P2-7 完善 WebGL 兜底

- 启动前区分 WebGL/WebGL2 能力与初始化异常。
- 错误界面提供“重试”按钮，并给出可执行的简短说明。

## 推荐实施批次

1. 第一批：P0-2 阵亡同步、P0-4 操作高亮、P0-3 回合与阶段提示。
2. 第二批：P0-1 规则/内容接线、P1-2 字体方案。
3. 第三批：P1 其余项目与全部 P2 打磨。

## 发布前统一验收红线

- HUD 不显示与规则不一致或永不变化的数据。
- 敌方意图、移动范围、攻击目标、行动阶段均可被玩家直接读懂。
- 320px 手机、平板竖屏和常见桌面宽度均可完成完整玩法闭环。
- 键盘焦点、禁用、选中、加载、错误、回合切换均有独立且一致的状态表现。
- 不新增重型框架、图标库或高包体方案；构建后继续记录 JS、CSS、字体、模型和完整资源体积。
